### Источник размера RX и назначение STOP

artifacts/reagent.jpg: подпись под штрихкодом визуально читается как
90222260300810701,17цифр. Это не UART-декодирование и не максимум всех этикеток.

управляемой отмены незавершённой попытки, включая плановую подготовку reset.

### Согласованный следующий блок F002/F006

1. Сохранить немедленный AppSafety_PrepareReset latch/safe GPIO по HC/общей
   инструкции. После latch обычный Wake/Send/START запрещён, latch не снимать.
2. Задача Scanner завершает/разбирает прерванный SSI-обмен. Старый ACK
   не принимать за ACK на STOP; отменённый запрос не выдавать успешным.
3. Добавить отдельный ограниченный путь выключения, допускающий только STOP
   после latch. CTS/RTS handshake без активации AIM; CTS LOW может разбудить
   SE965HP по table1-2. Это доменное дополнение, готового аналога HC нет.
4. Только после подтверждённой остановки закрыть RX и опубликовать prepared.
   Затем F002 service/reboot или F006 Flash/service/reboot. При ошибке/сроке
   prepared не публиковать, Flash не начинать, сохранить terminal failure path.
5. Общий бюджет3s вместо текущего1s: включает ожидание задачи, прежний обмен,
   STOP и подтверждение. Не добавлять3s на каждый этап или сбрасывать общий срок.

До выдачи кода подготовить весь связный блок: условия необходимости STOP
при idle/ошибочном/незавершённом состоянии, старые ACK/частичный TX,
post-latch RX и единый deadline. Сейчас Wake/Send/StartRx и RX callback
после latch запрещают продолжение; обычный вызов STOP там не заработает.
Не ослаблять общий gate ради произвольных UART-команд. Аварийные fault/
watchdog paths остаются без RTOS/UART waits. Физическое гашение при отказе
связи/аварийном reset этим программным порядком не гарантировано.

После этого отдельный блок F003: BUSY при активном scan/capture/UART-обмене,
с исключением гонки между проверкой и началом Flash, включая queued/in-flight.
Сейчас F003 прямо вызывает Commit; config mutex не останавливает UART.
Flash program/erase блокирует выборку кода из Flash на F103 и может привести
к потере UART. Автоматически рвать текущую операцию ради Commit не выбрано.

- SSI Length=4+payload, checksum MSB-first и корректная проверка; golden START
  `04 E4 04 00 FF 14`, ENABLE `04 E9 04 00 FF 0F`.
- Повторный запуск разрешён после ERROR/DATA_READY, активный SCANNING busy.
- Перед ENABLE/START/STOP/запросами: отдельный00, завершение TX, >=10ms пауза.
  Длительность выхода из сна по SE965HP до8ms; ACK на00 не ожидается.
- Общий service F020/F021, D501 raw last-RX и D502 retained START TX;
  общий модуль UART-диагностики Studio с профилями плат, без новой панели.
- CAN0603 версия (SSI A3), CAN0604 BEEP (E6,data00). Запрос без параметров;
  захват3s до192байт, schema1/flags/length16/errors32/raw, padding6.
  DONE означает конец захвата, не правильный SSI. D502 сохраняет START,
  не wake/revision/beep. Studio показывает сырой RX, отдельно проверяет SSI.

### Оставшиеся ограничения — не потерять при продолжении

- Studio иногда пишет Capture ended without DONE/NACK при фактическом DONE:
  main.py использует состояние фонового _domain_observers; локальный observer
  0603/0604 уже видит terminal. Исправление и regression test ещё не выполнены.
- Scan task реагирует на первое RX-событие; ACK не должен завершать ожидание
  штрихкода. Default module raw barcode и ожидание SSI DECODE_DATA прошивкой
  ещё не согласованы. RX DMA/re-arm/сборка полных SSI-пакетов требует проверки.
- Нет достоверного контроля готовности/ACK startup ENABLE, неизвестны уровни
  остальных неподключённых входов. Полная аппаратная приёмка не завершена.

### Подключение следующей ревизии

См. SCANNER_CONNECTION_20261027.md. Пользователь обсуждал вывод CTS/RTS,
TRIG,AIM/WAKE,PWRDWN на MCU. Конкретные свободные GPIO ещё не назначены.
Подтяжки10кОм — проектная рекомендация, не всеобщее требование производителя.
Ёмкости на управляющие линии для «снятия неопределённости» не добавлять:
на active-low входах они способны создавать запуск при включении питания.

Следующая сессия: сначала выяснить, изменена ли плата/шлейф и каким стал CTS;
если добавлены GPIO — согласовать реальные номера и реализовать SSI handshake.
Если остаётся только UART — проверить петлю и сигналы на модуле. Не утверждать,
что связь восстановлена, без принятого сырого ответа/валидного SSI.

## Общие Правила Работы

**Уточнение28.10.2026 по прямому поручению пользователя:** действующая
редакция правил вынесена в [WORK_RULES.md](WORK_RULES.md), согласована
по последним правилам Sensor/§4 Thermo. Перед продолжением читать её.
Старый текст ниже сохранён как история; текущий режим — консультационный,
без самостоятельного редактирования firmware. Техническая точка останова
этой правкой правил не повышается и не объявляется завершённой.


Этот раздел почти статичен. Он корректируется только при явном изменении правил
работы.

- По умолчанию работа идет в режиме консультации: сначала обсуждается
  архитектурное решение, затем даются точные блоки кода для внесения.
- Firmware-код пользователь вносит сам, если отдельно не разрешен режим
  исправлений или конкретная самостоятельная правка.
- После внесения изменений пользователем ассистент делает аудит проекта на
  корректность внесенных изменений.
- Для firmware-правок ответ дается в формате: файл, место, действие
  `ВСТАВИТЬ` / `ЗАМЕНИТЬ` / `УДАЛИТЬ`, блок кода, краткое обоснование.
- Предоставляемые блоки кода должны содержать смысловые комментарии: они
  объясняют назначение логики, границы ответственности и причину решения, а не
  пересказывают очевидные операции построчно.
- Каждый блок кода должен быть разделён на секции с заголовочными комментариями
  вида `// --- название секции ---`. Это относится к файлам, где добавление
  кода превышает 10-15 строк.
- Файлы, которые создаются целиком (new file), должны иметь заголовочный
  комментарий каждой функции/секции, а не только общий comment на весь файл.
- Отчеты, планы и checklist можно корректировать по ходу работы, но ранее
  внесенную информацию нельзя удалять; только добавлять или уточнять.
- Файл быстрого входа / handoff (`NEXT_SESSION_PROMPT.md`) не корректируется
  после каждого рабочего шага. Он обновляется только в конце дневной сессии и
  только по прямой просьбе пользователя.
- Технические решения должны соответствовать промышленному уровню DDS-240;
  упрощение допустимо только если advanced-подход неэффективен для задачи.
- Если задача или рекомендация пользователя противоречит принятому уровню
  проекта, ассистент обязан прямо указать на риск и предложить корректный
  вариант.
